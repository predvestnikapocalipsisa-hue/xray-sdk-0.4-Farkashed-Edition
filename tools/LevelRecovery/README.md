# Восстановление собранных уровней

## Текущее состояние

Версия 0.3 восстанавливает **редактируемую геометрию статики и растительности**:
библиотеку `.object` и расстановку экземпляров `.selection`. Полное восстановление
игрового уровня с материалами и физикой ещё не готово. Пункт LevelEditor:
`Scene → Recover compiled level…`. Чтение и экспорт выполняются в фоне.
В поля вводятся пути к каталогу собранного уровня и новому каталогу результата.
Исходный уровень не изменяется; существующий каталог назначения отклоняется.

Поддерживается конкретный профиль: заголовки level 13/14, OGF 4,
отдельный `level.geom` с декларациями DX9, GCONTAINER, статические и
прогрессивные меши, TREE_ST/TREE_PM, CFORM 4. На реальном уровне проверена
версия 14. Версия 13 проверяется синтетическим образцом. Это не обещание
поддержки любого уровня ТЧ/ЧН/ЗП: встроенные VB/IB, старые FVF, сжатые
чанки, другие версии CFORM и изменённые модами схемы пока отклоняются.
Общие номера версий не доказывают совместимость нестандартных шейдеров.

Ядро не зависит от D3D, Python, стороннего конвертера и глобального состояния
редактора. Один и тот же C++ код используется SDK и консольной утилитой.

## Этап 0.3: статическая геометрия и общая сцена

Связность рассчитывается по точным координатам через границы компиляционных
мешей. Совпадающие треугольники, включая обратные стороны, участвуют в
анализе смежности один раз, но **каждый исходный треугольник остаётся в
экспорте**. Рёбра с более чем двумя различными гранями не объединяются.
Это устраняет ложные разрывы из-за дублированных сторон без удаления сетки.

Повторы ищутся по геометрии, UV, нормалям и материалу. Квантованный ключ
служит только для поиска кандидатов. Общая модель допускается после точной
проверки float32-координат с переносом, атрибутов, порядка обхода граней и
взаимно однозначного соответствия вершин. Повороты и масштабирование статики
пока не распознаются. Если перенос начала координат теряет точность хотя бы
одной вершины террейна, на соответствующей оси сохраняются мировые координаты.
Сварки, упрощения и перестроения сетки нет.

Результат для `predbannik`:

| Показатель | Значение |
| --- | ---: |
| Статические группы связных поверхностей | 29 750 |
| Уникальные статические модели | 28 719 |
| Статические треугольники, сохранённые в расстановке | 1 059 894 |
| Треугольники статической библиотеки | 1 036 754 |
| Сохранённые совпадающие копии граней | 30 313 |
| Неоднозначные рёбра | 3 886 |
| Объекты общей расстановки вместе с деревьями | 33 117 |

Это группы поверхностей, а не доказанно восстановленные авторские объекты.
Связность сама по себе не отделяет приваренный стол от бара. Исходные имена
и границы объектов, уничтоженные компиляцией, требуют других свидетельств.
Исходная библиотека `.object` не нужна для текущего экспорта; парный набор
исходников и сборки другой локации пригодится для оценки следующего этапа.

В окне восстановления кнопка `Export native geometry scene` создаёт пакет,
а `Import recovered geometry into scene` устанавливает библиотеки и загружает
расстановку в сцену без статических объектов. Для ручной установки нужны
оба каталога: `objects/<static namespace>` и
`vegetation/objects/<tree namespace>`. После установки открывается
`geometry.selection`. Чтение/экспорт работают в фоне; импорт через SDK
синхронный и на таком количестве объектов может занять время.

`static_faces.csv` связывает каждую грань модели с исходным visual, гранью и
циклическим поворотом её индексов. `static_parts.csv` сохраняет исходный
шейдер, `static_instances.csv` — переносы, `static_models.csv` — библиотеку.
`original.cform` побайтно совпадает с исходной коллизией и не импортируется
как render-объект. Физические материалы и compile shaders ещё не сопоставлены:
preview использует `editor\\wire`, а Build/Make Game блокируются. Данные
исходных нормалей архивируются, нормали preview пересчитывает SDK.

Независимая проверка `verify_scene.py` читает игровые VB/IB и нативные файлы,
проверяет каждую исходную статическую грань ровно один раз, winding, точные
float32-позиции и UV, архив нормалей, соответствие вершин, материалы,
расстановку и коллизию. Затем запускается проверка деревьев. Сборка DLL
проверена; живой импорт в окне редактора и игровая производительность пока
не проверялись. Lightmaps, details, сектора, порталы и spawn не восстановлены.

## Этап 0.2: целые деревья и экземпляры в SDK

Сначала выделяются общие геометрические прототипы по исходным диапазонам
GCONTAINER, выбранному LOD-окну **и шейдеру**. Локальные координаты
сохраняются при чтении VB, до применения матрицы. Обратное преобразование
мировых вершин для получения библиотечной модели не используется.

Затем читаются исходные связи `OGF_CHILDREN_L` у LOD-визуалов. Если все
дочерние визуалы — растительность с одинаковой матрицей и однозначным
родителем, они восстанавливаются одним объектом с несколькими мешами и
поверхностями. Так ствол, ветки и крона остаются вместе. Совпадение матриц
без исходной связи не является основанием для объединения. Сложные или
неоднозначные группы остаются отдельными частями; это не угадывание
принадлежности к исходному авторскому объекту.

Для `predbannik` получилось:

| Показатель | Значение |
| --- | ---: |
| Исходные tree visuals | 7 003 |
| Геометрические части с учётом материала | 223 |
| Целые модели `.object` | 110 |
| Экземпляры `.selection` | 3 367 |
| Потерянные/исключённые экземпляры | 0 |
| Треугольники в общей библиотеке | 271 804 |
| Треугольники в развёрнутой растительности | 2 663 908 |
| Максимальное расхождение после SRT в float | 0,0000610352 м |

Сжатие по числу сохранённых треугольников составляет около 9,8 раза.
Это уменьшение дублирования геометрии, не замер ускорения игрового рендера.
Все позиции, индексы, UV, сохранённые нормали, связи исходных групп и
расстановка проверяются независимым скриптом `verify_native.py`.

Порядок работы в редакторе:

1. Открыть `Scene → Recover compiled level…` и указать каталог уровня.
2. Нажать `Read and analyze`, затем указать **новую** папку экспорта.
3. Нажать `Export native tree library`.
4. В сцене без существующих статических объектов нажать
   `Import vegetation into scene`. Объекты устанавливаются в отдельное
   пространство имён настроенной библиотеки SDK. Перед изменением сцены
   каждый `.object` читается настоящим загрузчиком SDK. Импорт добавляет
   одну операцию Undo. Изменённые пользователем библиотечные файлы не
   перезаписываются; повторная установка идентичных файлов допустима.

Альтернатива: скопировать каталог из `objects/` результата в настроенную
библиотеку объектов SDK и открыть `trees.selection` через
`File → Open Selection…`.

В нативном пакете есть `objects/<namespace>/tree_*.object`,
`tree_*.normals.bin`, `trees.selection`, `prototypes.csv`, `model_parts.csv`,
`instances.csv` и `tree-recovery.txt`. Полные исходные матрицы, соответствия
визуалов целым объектам и коэффициенты tree lighting сохраняются в CSV.
Namespace содержит версию экспортёра и отпечаток содержимого `level` и
`level.geom`; отпечаток используется как имя, не как доказательство
равенства мешей. При установке существующие файлы сравниваются побайтно.

Матрицы переводятся в положение/поворот/масштаб SDK. Поддерживаются
неравномерный масштаб и отражение; shear и вырожденные преобразования
не аппроксимируются скрыто. Каждая вершина проверяется после обратной
сборки SRT с допуском 0,0001 м. Не представимые в SDK экземпляры остаются
в `instances.csv`, исключаются из selection и учитываются в отчёте.
Автоматический импорт из окна восстановления в этом случае останавливается
до изменения библиотеки и сцены; частичный selection можно открыть вручную
после проверки отчёта.

**Материалы ещё не восстановлены.** Для предпросмотра установлен
`editor\\wire`; исходные шейдеры и текстуры сохранены в `model_parts.csv`.
Compile shader и физический материал помечены `__recovery_unmapped__`.
Валидация SDK блокирует и Build, и Make Game, пока render shader,
compile shader и физический материал явно не сопоставлены. Предпросмотр
`editor\\wire` у помеченных восстановленных объектов также блокирует сборку.
Коллизия из полигонов деревьев не создаётся декомпилятором. Исходный CFORM
сохранён прежним общим экспортом; в сцену растительности он не импортируется.

Стандартный `.object` SDK не хранит произвольные исходные split normals:
при отображении SDK пересчитывает нормали по сетке. Декодированные локальные
нормали сохранены отдельно в `*.normals.bin`: `XRNORM01`, u32 количества
вершин, далее float3 для каждой вершины, в порядке мешей объекта.
Это архив исходных данных, не автоматически обновляемые нормали после
редактирования. Baked lighting, ветер и исходные LOD-прокси пока не
восстанавливаются в нативных объектах. Автоматическое объединение крупных
статических batches в дома/столы/террейн в этот этап не входит.

## Что уже сохраняется

- Треугольники и позиции собранной геометрии без упрощения, ремешинга,
  пространственной сварки или удаления вырожденных граней.
- Декодированные нормали и базовые UV, включая дробную поправку в
  альфа-каналах tangent/binormal. Это данные компиляции, не исходные
  авторские нормали или точность UV до упаковки.
- Максимальный уровень детализации прогрессивных мешей: окно 0,
  с учётом его offset, num_tris и num_verts. LOD-прокси не добавляются
  поверх полноценной геометрии.
- Преобразования экземпляров растительности в мировые координаты.
  Несвязанные карточки листвы одного tree visual остаются одной группой.
- Исходные 16-байтовые записи треугольников CFORM, включая 14-битный индекс
  физического материала, флаги теней/wallmark и сектор. `original.cform`
  копируется из прочитанного снимка побайтно; коллизия не строится из render.
- Связь каждой экспортированной грани с visual, номером грани выбранного
  LOD, группой и таблицей шейдеров исходного уровня.

Экспорт: `render.obj`, `render.mtl`, `render_faces.csv`, `materials.csv`,
`collision.obj`, `collision_faces.csv`, `original.cform`, `visuals.csv`, `report.txt`.
В `visuals.csv` сохранены исходные диапазоны GCONTAINER, смещение выбранного
LOD и матрицы экземпляров. Это позволяет отличать повторное использование
одной геометрии от независимых мешей; OBJ разворачивает экземпляры для осмотра.
OBJ сохраняет оси и порядок обхода X-Ray; V меняется на 1−V.
MTL содержит нейтральные материалы для осмотра. Имена шейдеров и полные
списки текстур хранятся в CSV; текстуры и alpha flags не подставляются
наугад. Ветер, освещение и физическое поведение не представлены в OBJ.

Не импортируйте такой OBJ как готовую игровую сцену с материалами по
умолчанию: это снова смешает render и collision и потеряет свойства игры.
Для физики нужны материалы **того же gamemtl.xr**, включая их порядок,
а не совпавшие номера материалов текущего SDK. Библиотека может находиться
в игровых архивах, даже если её нет рядом с каталогом уровня.

## Группировка и её границы

Для статической геометрии строится граф граней по точно совпадающим рёбрам
в мировых координатах. Разные материалы и UV-швы не мешают объединению;
касание одной вершиной и небольшое расстояние между объектами не являются
основанием для объединения. Позиционные ключи используются только для
анализа: исходные вершины не свариваются. Экземпляры растительности
изолированы друг от друга и статической геометрии.

Рёбра с более чем двумя инцидентными гранями отмечаются как неоднозначные;
алгоритм не выбирает пару автоматически. Это консервативный режим, который
может оставлять много фрагментов. Группа связности — кандидат поверхности,
а не доказанно восстановленный стол, дом или террейн. Результат не выдаёт
такие кандидаты за исходные авторские объекты.

## Архитектура следующих этапов

1. **Профили форматов.** Отдельные адаптеры ТЧ, ЧН, ЗП и конкретных модов;
   определение по содержимому и проверкам диапазонов, а не имени папки.
   Добавить образцы каждой игры, старые layouts и сжатие. Неизвестные чанки
   сохранять вместе с диагностикой и не трактовать по догадке.
2. **Восстановление объектов.** Сначала искать совпадения с имеющимися
   `.object`/OGF в библиотеке: геометрические сигнатуры, локальная система
   координат, затем проверка преобразования и совпадения граней. При
   уверенном совпадении возвращать ссылку на объект и transform. Для
   остальных — граф границ, признаки материала/нормалей/UV, поиск повторов
   и ручное разделение/объединение с привязкой к исходным граням.
   Имена объектов и принадлежность деталей, удалённые компилятором,
   в общем случае невозможно восстановить однозначно.
3. **Террейн.** Сохранить текущую триангуляцию и все каналы UV. Склеивать
   логические группы через границы компиляционных batches, не менять
   координаты. Если нужна новая сетка — отдельная операция с измерением
   отклонения, никогда скрытый шаг декомпиляции.
4. **Физика.** Читать библиотеку материалов исходной игры, сопоставлять
   материалы по смыслу/имени и флагам, сохранять исключения. Показывать
   render и CFORM разными слоями. Несовпадение не доказывает ошибку:
   упрощённая коллизия и невидимые барьеры могут быть авторскими.
   Не удалять их автоматически и не создавать коллайдеры для каждого куста.
5. **Редактируемая сцена SDK.** Экспорт `.object` и сцены с независимыми
   render/collision-поверхностями и верными compile shaders; сектора,
   порталы, HOM, details, освещение и spawn отдельными обработчиками.
   Импорт в новую сцену, журнал потерь/неопределённостей и возможность
   повторить восстановление с исправленными решениями.
6. **Проверка перекомпиляцией.** Сравнить треугольники и UV до импорта и
   после экспорта; затем CFORM и материалы, сектора/порталы, размеры
   buffers и draw calls. Производительность измерять в движке на одинаковых
   маршрутах камеры. Число объектов само по себе не является её мерой.

ML-сегментация может предлагать границы объектов и имена, но не должна
менять геометрию или физику без проверяемого соответствия исходным граням.
Приоритет — воспроизводимое восстановление и сопоставление с библиотекой.

## Сборка и проверки

Из Developer PowerShell Visual Studio:

```powershell
MSBuild tools/LevelRecovery/LevelRecovery.vcxproj /p:Configuration=Release /p:Platform=x64
MSBuild tools/LevelRecovery/LevelRecovery.vcxproj /p:Configuration=Release /p:Platform=x64 /p:RecoveryTests=true
./output/LevelRecovery/LevelRecoveryTests.exe
./output/LevelRecovery/LevelRecovery.exe 'E:\STSoC Weapon Pack 2.0!\gamedata\levels\predbannik'
./output/LevelRecovery/LevelRecovery.exe '<source-level-folder>' '<new-export-folder>'
./output/LevelRecovery/LevelRecovery.exe --trees '<source-level-folder>' '<new-native-export-folder>'
python tools/LevelRecovery/verify_native.py '<source-level-folder>' '<native-export-folder>'
./output/LevelRecovery/LevelRecovery.exe --scene '<source-level-folder>' '<new-scene-export-folder>'
python tools/LevelRecovery/verify_scene.py '<source-level-folder>' '<scene-export-folder>'
```

Тесты покрывают рёбра через границы материалов, касание одной вершиной,
отсутствие сварки близких точек, целостность tree instance, неоднозначные
стыки, UV-поправку, окно прогрессивного меша, CFORM-атрибуты, повреждённые
входные данные и отказ от записи внутрь исходного уровня/поверх результата.
Для нативного этапа проверяются повторное использование геометрии,
различие материалов, сборка ствола и кроны по LOD-связям, неоднозначные
родители, SRT с отражениями и неравномерным масштабом, gimbal lock, отказ
на shear/нулевом масштабе, структуры `.object`/`.selection`, повторная
установка и защита изменённых библиотечных файлов. Независимый Python-аудит
использует только стандартную библиотеку и читает исходные игровые буферы.

Для редактора используется обычная сборка `Build-SDK.ps1 -Module LevelEditor`.
Если в окружении не собирается LuaJIT, отдельно проверить модуль с уже
собранными зависимостями можно через `/p:BuildProjectReferences=false`.
Это проверяет редактор, но не заменяет полную сборку комплекта SDK.
